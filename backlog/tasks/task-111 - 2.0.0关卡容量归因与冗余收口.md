## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
**本次 v2.0.0 Release 容量专项，允许立即独立开展，不等待 TASK-103 或全部产品/UI 完成人工验收；硬依赖为空。** 在保留岩系旅行者、前两幕、已批准视觉/功能、规则与交互的前提下，定位关卡存档反复逼近/超过官方 20MB 上限的真实主要成本，并按收益完成必要的最小冗余收口。发版前必须有**最终同一候选**的官方容量通过证据。

历史证据分别是 70.51413MB/20MB 的 V25 静态展开失败、旧 8.96MB 基线、其他 19.78MB 可导入候选及 Owner 的 20.1781MB 超限截图；**彼此未绑定同一候选身份，不得直接相减、伪造增长曲线或归因占比**。源码/GIL 文件大小、Git pack、模拟器控件数均不等于官方存档读数。16MB 是争取的内部余量目标，不是替代官方的硬限制。

**与已有任务划界：** TASK-10.1.2 负责卡图/多实例与手机专项；TASK-100 负责运行时性能热路径；TASK-105 仍属 M9 新增角色边际成本及 10/20/30 角色量产准入，TASK-97 仍依赖 TASK-105。本任务只负责当前 2.0.0 整包容量归因、可证明的冗余修复与防复发；引用上述任务但不要求它们先完成，也不接管未来角色量产。

- [ ] #2 产出**可复核的容量账单**：从实际生产映射和 GIL 读回按 Lua（玩法/配置/界面/绘图）、原生 UI 页面/模板/卡面宿主、隐藏/重复结构、角色/怪物/遗物/背景及基础场景分类；列 Top 大户的具体文件或控件路径、字节、实例数、来源生成器、是否本版必须，并区分离线大小与官方估算。优先核查 38 个完整卡面宿主、V25→official 多层装配、旧图层及未开放原创 V4 角色的打包边界，**不得预设主因**。
- [ ] #3 用同一干净 C0 构建进行单因素 C1…Cn 诊断：卡面、其他 UI、可选美术、非本版数据分别隔离，验证候选身份、差异清单、构建/读回合法性，尽可能取得各项**官方存档容量差值**；不同组非线性/交互成本再做组合测量。未经官方同条件实测不把减掉的源码字节或 UI 节点数说成节省的 MB。
- [ ] #4 对确定存在且收益可量化的非必要结构执行**最小、可回滚修复**，优先处理错误重复装配、遗留装饰/失效宿主及本版不需携带但研发端必须保留的数据；不删核心规则、合法 10 手牌/敌人/事件，不改卡面批准稿、视觉层级、手机命中或 RNG。修前修后逐屏/输入/生命周期/同局流程保持等价。
- [ ] #5 复用 `check:platform-load`、`verify:platform-load` 和现有 CI：提供按模块/页面/资源的增量排名与证据告警，保持现有预算、旧快照、负例及严格来源合同；无经过官方校准的 MB 公式时只做离线预警，不虚构官方通过，也不为此放宽 Full/Required 或加入重型实机 CI。
- [ ] #6 最终**实际准备发布的同一冻结 RC** 官方关卡存档 ≤20MB、服务器 ≤3MB，并取得可核实截图/报告、官方导入/ready 和受影响 PC/实体手机功能与加载/内存回归；优先争取 ≤16MB 的长期内部预算与合理扩展余量，若未达到须披露差距和风险。缺本轮官方/设备证据时保持未验，不宣称发布 GO；实现 PR 正常独审/Required CI，发布操作仍由 Owner 执行。
