# 怪物原生图元池按档分配：离线设计试验

目的：保持第三／四批原生稿的画面，避免同屏小怪按最大怪物分配绘图槽。基线 Release `33d71575c5f186a1b54f7bf3e4f1826c145aa1d9`。使用正式 GameUI / Combat / MonsterArt / CardDisplay 与原生控件 mock；装配、换绘图子树和选档逻辑只存在于本目录测试夹具。生产开关仍未启用。

| 实际房间编组 | 可见图元 | 115 槽全池 | 41／115 分档 | 少预留 |
|---|---:|---:|---:|---:|
| 三赤甲虫（3 Louse，全红分支） | 123 | 345 | 123 | 222（64.3%） |
| 赤甲虫＋祈火徒（Exordium Thugs 相应分支） | 156 | 230 | 156 | 74（32.2%） |

表中是测试设备层的**预留绘图槽**，不含绘图容器、HUD/状态实例，不是运行时间或 GIL/官方容量。随机边界选定真实编组，不声称回放原始随机流。此试验先将保留目录的测试输入裁到第三批＋中草兼容稿；原整库仍是 600 槽，不得把分档结果写成生产现状。第四批两只 113／114 图元本身已近 115 档，分档主要省小怪的过度预留。

## 为什么不能只在初次创建时选档

- 负对照 `fixed`：在相同 actor ID/控件上注入一个完整源规格演员，测试从 41 图元换到 115。初始化后锁档会因 `missing native art slot` 落回旧图库；同档普通编组仍通过。这个换 ID 测试是人造边界，不声称已观察到正常战斗中同一 actor ID 改种类。
- 试验 `art-only`：仅释放旧画面根、换新根并重新装载原有 renderer；41→115→41 两次替换通过，旧画面控件回收。actor 根、原来的命中监听、血条、意图、状态行、同屏另一个小怪均保留；点击原命中控件能把真实卡牌伤害打给原槽的正确演员；随后退休也不误回收另一只。
- 现行生产 actor 真实 ID 在构造时来自 definition，召唤／分裂会使用新的 serial；目前未找到正常玩法对同 ID 改 definition 的路径。若以后实施，可先只对已证明定义稳定的怪物创建小档，其他留大档或图库；进一步切换时保留 HUD／命中根，持有返回的子树句柄。**不知道官方引擎能否在现成控件下用名字枚举新模板根**。测试直接用 mock 子节点字典装配，不能代替原生 `InstantiateClientUIControl`、返回句柄、层级导航、销毁异常、180° 动画、真机等验收。这里不改正式绑定或候选包。

## 复现

锁定仓库 Node/Fengari 测试依赖后，准备第三批原生结果、兼容中草结果：

```sh
export RELEASE_REPO=/path/to/exact-release
export BATCH03_DIR=/path/to/monster-pilot-03
export ACID_MEDIUM_LAYOUT=/path/to/acid_slime_m/native-layout.json
node run.mjs fixed    # 标为 EXPECTED_NEGATIVE_FIXED_TIER 才算负例通过
node run.mjs art-only # 两个编组、两次 art 子树替换、定向、退休
```

归档只存夹具、重跑脚本和原始结果，不存构建目录或生成 Lua 大样本。
