## 2. 规模实验和限制

按四套冻结 V4 的真实 75 卡+职业规则循环采样，替换稳定 ID/职业 ID，生成新增 0/1/2/10/20/30/100 套；校验总卡数及 ID 唯一。独立单角色样本分别 142,447 / 141,860 / 149,767 / 137,183 B，规则和中文文本也参与真实序列化，非用源码文件大小平均后乘 N。

新增量均在已有四套 V4 之外，即 +20 是 24 套 V4 数据，+30 是 34 套；这比“最终总共20/30”保守，不能误标为总数。旅行者现有普通卡池另在 abyss_data。本轮不把这些压力 ID 注册成可玩职业，也不伪造未来新机制/文案的成本。

每档写入实验生成目录的两个既有模块位置，调用正式 `candidateScriptFiles` 读取361模块，核对实际字节总和，然后恢复原生成文件。数据 Lua 语法全部解析，重复美术包在 0/1/2 档语法解析，全部压缩证据读回逐字节一致。没有为每档重建 GIL，也没有运行这些合成角色。卡牌文本/机制也只来自四种真实样本，会大量重复；因此连卡牌数据的压缩率也不能代表未来独立文案/机制的压缩率。没有把任何gzip结果用于拟合官方容量。

四档定义：

1. **independent 正常独立美术压力档**：每新增角色再内嵌一份当前完整真实角色包，保留共享布局/模板，不复制整个 UI。是真实资产负载的重复装配，不是 N 张新图；唯一美术内容 digest 始终只有1种，因此平台若压缩重复，会过于乐观。
2. **trimmed 最小装配优化候选**：同上，仅在实验缓冲区移除 selection133 字段，每份包减少128,378 B（含分隔符）。当前 official 分支选择 battlePixel，战斗选择批准待机；保留 battle133 的结果页/其他分支用途。其余字段原文不变。静态路径支持该候选，尚未做替换包的完整运行时/官方证明，未改生产生成器。
3. **shared 共用美术档**：全部角色共用当前一份角色包，新增75卡和规则；不复制宿主/布局。此档验证序列化成本下界，意味着没有新增独特肖像/待机，不能将该节省用于承诺30套独特美术。
4. **fallback 极限保底档**：现有开关全部关闭，保留数据和玩法源码，使用已有基础 UI/素材路线。构建器不支持 official-assets 搭配全关肖像或普通皮肤搭配 nativePageLifecycle，所以此档还切回普通 UI/生命周期，属于组合保底，不是同皮肤单变量肖像消融。正式产品是否接受需另行决定。

## 4. 20 MB 长期情景与最小保底

令L0为今晚当前正式B0的**官方面板MB**，d为两个代表性角色中较大边际成本（需包含独特美术），R为第三/第四幕和未计内容预留，则 `L0 + N*d + R` 只在同条件近似线性、并补过大规模点后才可作规划模型；16MB内部目标与20MB硬限分别代入，不能把上面Lua字节代入L0/d。

| 情景 | 资产/章节假设 | 本轮支持程度与决策 |
|---|---|---|
| 乐观 | 共享宿主/UI，官方ID素材或共用一份角色画；章节主要复用既有逻辑 | 数据新增约0.143MB源码/角色已测，官方delta未知；最有希望保20～30，但放弃完整独特肖像/待机的成本下界不等于成品质保 |
| 基准 | 每角色独特头像/待机，UI固定；按实际可消除字段裁剪 | 每角色约1.07MB离线输入边际（trimmed），+30仅裁剪仍约37.05MB总Lua；必须取得官方delta才可判断，不声称稳在20MB |
| 悲观 | 每角色整包美术、进一步每卡独特精绘/多章独特场景；不能共享的数据很多 | 独立包每角色约1.20MB离线边际；75张精绘、额外动画/音频未纳入，真实最坏还可更大；无有界的“绝对最坏上限”，应停止按此路线批量生产 |

没有官方数据时不提供伪精确的MB置信区间。用于今晚判定的**假设预算例子（不是测量）**：若L0=12MB且R=2MB，20/30角色要守16MB分别需d≤0.100/0.067MB，守20MB需≤0.300/0.200MB；若L0=16MB、R=2MB，则内部目标已无空间，硬限20/30角色仅剩≤0.100/0.067MB。R=2MB只是显式规划变量，不是第三/四幕实测。未来总20/30可按实际新增人数重算。

最小可行保底次序：先保持一份共享框架/宿主，查清并裁掉同候选实际不消费的绘图字段（本轮给出128,378B候选）；不复制布局、卡框和引擎。若官方仍超预算，优先牺牲每角色独特高图元肖像/完整待机与逐卡精绘，保留75卡规则、中文说明、ID、战斗/奖励/跨幕状态，用现有官方素材/共用符号区分角色；关闭绘图只能在实验/批准的后续产品变更中执行。再复用章节场景/音效，减少章节专属装饰。若此档官方仍无法容纳20～30角色与四幕，应缩小单关卡开放角色/内容批次（保留full-source研发资料），不能靠删核心规则、提高负载档位、升级账号、引入后端或伪造读数保项目。任何产品取舍都未在本轮实施。

## 5. 今晚 GI 最小测量单

本轮没有键鼠授权；以下是待执行步骤，不是已完成记录。正式设备验证、动态报告、完整P0/RC门禁不因这个最小容量实验而免除。

1. 先冻结同一干净源码和客户端版本，复用本轮已验基础GIL/参数，重新生成可测B0，记录sourceSHA/buildId/candidateSha256/payloadDigest/生成时间。当前带dirty标识副本可做预检，不作为最终冻结证据。每个候选单独存档副本，不覆盖用户存档。
2. 导入B0，保存后打开官方负载/存档面板，记录关卡和服务器数值、单位、上限、时间与脱敏截图。GIL字节单列；上传进度/网络量不代替面板。
3. 同基线准备B1、B2：分别加入第1/第2个代表性角色，按数据→独特头像→独特待机分步装配记录。不改变已有宿主/UI池。若只启用已打包V4而无文件增量，其delta=0只说明解锁不增加存储，不代表新角色免费。本轮合成模块不能直接充当可玩B1/B2；先按原构建/装配合同做少量合法隔离候选，不需批量画30名角色。
4. B0、B1、B2每档都记录同套官方数值，算d1=L1-L0、d2=L2-L1；取较大边际，并考虑面板显示精度。为区分数据/肖像/待机，保留每步对应候选，不从一次总delta强拆类别。共用第二实例和第二独特资产分别测，避免把压缩重复图的delta当独特图delta。
5. 只补一个资源关闭保底候选，明确它与B0的皮肤/生命周期差异；不把合成30角色档或非代表性的压缩副本作为唯一测点。若小规模已逼近上限，直接测共享保底，避免无价值扩装。
6. B0/B1/B2与保底做真实启动/新ready、角色选择/战斗/切换/释放；每次新导入重新订阅且clientScriptLog:true。容量拟合足够后再按原平台合同补一个10或30角色规模点及章节组合点，实体手机复测，覆盖加载、切换、退出重入和释放；没有该大规模/章节与手机结果不签长期GO。

最小容量第一轮是4类候选（B0/B1/B2/保底），角色成本拆分需在B1/B2中额外保存分步变体，不能用4个总读数谎称类别均已解耦。对照截图/报告绑定各自身份，保留官方原始报告，不点发布。最后按 `npm run verify:platform-load -- <冻结candidate.json> <official-load.json>` 验证；没有完整证据预期仍UNVERIFIED/BLOCKED。
