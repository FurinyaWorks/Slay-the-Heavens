# 暖开弃牌堆：第 1 次更新由谁等待

用上一份已固定的 [12 张弃牌堆 Host](../README.md) 脚本和实际战斗 HUD 触点，在精确 Develop `b2f74d99` 和其上 #932 六个生产文件的本地逐文件三方投影，各执行一次冷开填池和一次暖开追踪。两组由相同 #951 生成数据与布局。只记录暖开；在探针中包裹实际 pool 和页面门禁方法，保留所有输入、返回和流程，过程中不输出，原生产文件无仪表改动。

| 模拟更新 | 两组相同的事件顺序 |
|---|---|
| 0，HUD 点击返回 | 同一个新浏览代次，10 个旧实体与分段已挂载。新代次模型 0、提交 0、`next=1`、`yielded=false`。 |
| 1 | pool 只把 `yielded` 改为 `true`，没有创建模型、提交新牌或就绪；随后页面门仍等待。 |
| 2 | pool 写入全部 10 个新代次模型/牌并设 ready，页面门同一更新发布，真实详情点击被接受。 |

因此这个 **离线暖开样本**的第一轮等待在牌堆池，不是池就绪后页面门再等一帧。已有挂载不是新代次内容已经就绪。#932 不显示视觉遮罩但逻辑输入守卫仍等到 ready，二者不可混同。此带观察器的顺序追踪不是 CPU 性能采样、真机帧数或安全删除 yield 的证明。设备仍慢时只需要这四个时点，不要先开性能模式、删除首反馈让步或放松过期触点守卫。

复跑：依照上级 README 应用其 `probe.patch` 生成 `battle-probe.lua`，再 `patch -o battle-trace.lua battle-probe.lua < trace.patch`；同等生成数据/UI 后以 `DECK_SAMPLES=1` 和同一 `DECK_ROSTER`、`DECK_GENERATED` 用 LuaTeX 运行。
